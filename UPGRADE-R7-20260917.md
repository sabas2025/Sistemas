# Instalação e atualização — R7 build 20260917.1

Leia primeiro este documento. Os relatórios R5/R6/R7 anteriores são históricos, não evidências desta compilação. O pacote foi modificado localmente; não houve implantação na VPS.

## Mudança operacional importante

Esta compilação exige **uma empresa por instalação**, vínculo explícito das credenciais globais Tiny/VSM e empresa atribuída ao usuário. Sem essas condições, as operações são bloqueadas; telas de configuração e manutenção continuam disponíveis para ajuste. Credenciais globais não autorizam multicliente.

Registros com `empresa_id IS NULL` deixam de aparecer nas consultas com escopo e não são retirados pelas filas principais, de estoque e fiscal. Eles NÃO são apagados: precisam de classificação comprovada. Não atribua todo o histórico a uma empresa sem verificar sua origem.

## 1. Antes de atualizar uma instalação existente

1. Trabalhe primeiro em cópia de homologação. Registre a versão atual e o banco usado por cada módulo.
2. Faça backup dos bancos e dos arquivos, incluindo `config/config.php`, chaves, anexos, XMLs e armazenamento externo. Restaure uma cópia e confirme os dados; checksum sozinho não comprova restauração.
3. Confira uma única empresa cadastrada e ativa em `empresas`. O instalador antigo cria uma empresa de demonstração: confira/corrija sua identidade antes de confirmar a propriedade das credenciais. Não exclua outras empresas para contornar o bloqueio.
4. Confira usuários e seus vínculos. A mudança de empresa/perfil/inativação exige nova autenticação.
5. Pare workers/crons e suspenda ou drene entradas externas durante a troca de código e schema. Preserve eventos pendentes para reconciliação.
6. Preserve o `config/config.php` real e todo o armazenamento. Não use o instalador de instalação nova sobre banco de produção existente.

O executor novo exige que o baseline Enterprise Core já exista. Se a simulação apontar tabela ausente, examine as migrations históricas até `20260713_007_enterprise_map_recovery.sql` e use a simulação da Central Técnica para esse baseline. Não aplica automaticamente SQL indiscriminado de versões antigas.

## 2. Simular e aplicar o upgrade

Execute da raiz do projeto (onde estão `app/`, `scripts/`, `database/`), com o mesmo usuário operacional do site:

```bash
php scripts/upgrade-r7.php --help
php scripts/upgrade-r7.php --dry-run
```

A simulação lê o banco, lista migrations/módulos/bancos e conta linhas NULL; não executa DDL/DML. O catálogo contém apenas 008–017. Ele preserva a sequência de `PREPARE`, `EXECUTE` e `DEALLOCATE`, sem divisão ingênua por ponto e vírgula.

Após confirmar backup restaurado e manutenção:

```bash
php scripts/upgrade-r7.php --apply --restore-tested --maintenance-confirmed
```

As flags são declarações do operador, não detectores automáticos de backup ou de workers parados. A fase padrão exclui BIGINT 012. Um lock MySQL no banco core impede outro executor desta release ao mesmo tempo. SQL executado manualmente por fora não respeita esse lock.

| Migration | Destino lógico | Tratamento |
| --- | --- | --- |
| 008 | core | Catálogo de permissões de backup |
| 009 | backups | Coluna/índice de procedência |
| 010 | módulos com dados empresariais | Colunas/índices; sem backfill por inferência |
| 011 | pedidos | Índices por empresa/status/data |
| 012 | pedidos, fila, observabilidade | Somente fase BIGINT ou all |
| 013 | observabilidade e core | Logs no primeiro; sessões no core |
| 014 | core | Vínculo dos usuários |
| 015–016 | fila | Índice redundante e índice de eventos |
| 017 | core | Tabela `myouro_conexoes` e `integracao_empresa_id` |

No modo banco único, destinos iguais são agrupados. No modular, os bancos vêm da configuração real do projeto. Os SQLs históricos não foram reescritos: o executor controla destino, registro e backfill na execução. Não misture esse procedimento com aplicação manual paralela.

### BIGINT — janela separada

```bash
php scripts/upgrade-r7.php --dry-run --phase=bigint
php scripts/upgrade-r7.php --apply --phase=bigint --restore-tested --maintenance-confirmed
```

Meça duração, espaço e locks com volume representativo. ALTER pode reconstruir tabelas e fazer commit implícito. Não há rollback transacional de todo o upgrade e não há conversão automática BIGINT → INT.

### Dados legados sem empresa

O padrão não atribui proprietário. Se houver evidência de que TODOS os registros NULL e usuários legados pertencem à única empresa, o executor oferece `--backfill-empresa=ID --legacy-ownership-confirmed`. Escolha essa política antes da primeira aplicação e use os mesmos parâmetros na simulação/aplicação/repetição. Trocar o plano depois de aplicado causa divergência de checksum e exige revisão manual. Não use essa opção para registros ambíguos. O parâmetro ID é o ID real, não um valor para copiar deste exemplo.

## 3. Após o schema

1. Abra `index.php?page=myouro-configuracoes`, também disponível pelo link em Configurações.
2. Como administrador, confira a empresa e confirme explicitamente o vínculo das credenciais Tiny/VSM. Isso altera só `integracao_empresa_id`, não tokens nem URLs legadas.
3. Em Usuários, atribua a empresa correta. Saia e entre novamente.
4. Valide banco, contagens, consultas, filas, DLQ e permissões antes de retomar os workers. Confirme a fase BIGINT separadamente.
5. Confira `VERSAO.txt`, a versão exibida e os metadados efetivos de `App::config()`: `V104.49.3-R7+20260917.1`. O arquivo de configuração existente não é regravado só para alterar metadados.
6. Reative integrações de forma gradual e acompanhe o primeiro ciclo completo.

O registro fica em `schema_migrations`, chaves `r7build20260917_XXX`, e em `storage/logs/upgrade-r7-*.jsonl`. Início fica marcado como falha até todas as pós-condições daquela migration passarem. Uma interrupção não vira sucesso. Guarde essas evidências fora do diretório público.

## 4. MyOuro — somente consulta

- URL completa fixa informada no relatório: `https://msx.vsm.api.br/graphql`.
- Ambiente: produção, somente leitura; loja e empresa explicitamente vinculadas.
- Cadastre o token sem `Bearer`. Ele é cifrado com AES-256-GCM e não é devolvido ao HTML. Campo vazio preserva o valor anterior.
- Acrescente `msx.vsm.api.br` em `security.vsm_allowed_hosts`, mantendo os hosts Tiny/VSM que já forem necessários. Não desative validação TLS/DNS para contornar erro.
- Habilite/salve e só então consulte um produto VSM conhecido. O código é inteiro do VSM, não SKU ou ID Tiny.
- POST carrega a query fixa `EstoquePorProdutoLoja` e variáveis separadas. Não há mutations, sincronização automática ou retry silencioso.
- `errors`, dados parciais, JSON inválido, loja/produto divergente e produto inexistente não são interpretados como integração concluída nem saldo zero.
- Um teste bem-sucedido valida apenas essa consulta/credencial/loja naquele momento, não toda a operação.

## 5. Instalação nova

Use o `public/install.php` protegido e o procedimento de autorização já existente (`php scripts/create-install-authorization.php`). Os módulos e consolidados já incluem os novos campos; não execute um script de reset. Depois configure a identidade da empresa, os vínculos dos usuários, o vínculo da integração e os tokens pelo painel. Não deixe a empresa de demonstração representar sua operação sem conferência.

## 6. Falha e recuperação

Mantenha workers e entradas suspensos. Guarde o log e identifique a última migration e o statement iniciado. Compare schema/dados com a cópia restaurada. A reaplicação usa SQL idempotente, mas não substitui diagnóstico de falha parcial. Se houver divergência de checksum, não apague o registro para forçar a continuação.

Rollback exige restaurar código e banco compatíveis e reconciliar eventos desde o backup. Voltar apenas o ZIP pode reintroduzir o isolamento permissivo anterior. Não apague a tabela MyOuro nem as colunas novas como primeiro passo de recuperação.

## 7. O que ainda impede homologação completa

Contrato REST oficial da VSM (homologação e produção), autenticação `clientToken/clientSecret`, endpoint/payload de criação, credenciais autorizadas, liberação do host e testes reais. Não foram inventados endpoint de produção, troca de token ou mutation. As melhorias de carga/p95, alertas, acessibilidade e restauração periódica exigem uma etapa operacional específica; não foram marcadas como concluídas.
